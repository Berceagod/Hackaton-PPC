# ADR-0011: Encryption at rest (AES-256-GCM, streaming, key derived per object)
Status: accepted (slice F)

Context: PDF §4 "an unauthorized direct access to a storage does not expose the personal data in connection documents"; §2.1 connection documents are "protected and verifiable at audit". Files can be > 1 GB and must stream (ADR-0010). Storages may be FTP, S3 or Postgres, chosen by policy.

Decision:
- Encryption is a per-category policy flag (`encryption: true`, on for `connection_docs` by default) and works for every category and every storage, including meter readings and chunked uploads.
- Data is encrypted inside the backend before it reaches any storage, with AES-256-GCM in 64 KB segments (`backend/crypto_envelope.py`, format `FGE1`):
  `MAGIC "FGE1" | 8-byte random nonce prefix | segments`; nonce = prefix || segment index; AAD = object id, index and a final flag. Each segment is authenticated before its plaintext is released. Truncation, reordering, bit flips and moving ciphertext to another file are all detected (`DecryptionError`). Memory is one segment.
- Key: one AES-256 key per object, derived with HKDF-SHA256 from the master key and the object id. The master key (`FILEGRID_MASTER_KEY`, 32 random bytes) is generated by `start.sh` / `start.ps1` into `.env` and exists only in the backend container's environment. No key material is stored in any storage or database. Deterministic derivation also means a meter-reading takeover that rewrites the same object (ADR-0004) produces a ciphertext the record can always decrypt.
- Chunked uploads: staged chunks of an encrypted category are encrypted too (object id `staging/<upload_id>/<index>`), so personal data is never at rest in clear, not even during an upload. The flag is fixed at the first chunk.
- `sha256` and `size_bytes` in the metadata are those of the plaintext (what the user uploaded and gets back). Download and `/verify` decrypt, authenticate and hash; a failure is `409` with reason `decryption_failed`, audited as `download_blocked`.
- Changing the policy affects new files only; each file's metadata row says whether it is encrypted.

Consequences:
- A copy of a storage, or of the metadata database, decrypts nothing on its own (proven by `scripts/demo/unauthorized-direct-storage-access.sh` on FTP, S3 and Postgres).
- Losing `FILEGRID_MASTER_KEY` makes encrypted documents unreadable: `.env` must be backed up. Rotation is not implemented: a new key version would need a version byte in the header and re-encryption of old objects.
- Ciphertext is 16 bytes per 64 KB larger than the plaintext, plus a 12-byte header.
