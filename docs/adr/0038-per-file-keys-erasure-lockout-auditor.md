# ADR-0038: Per-file keys (crypto-shredding), erasure, login lockout, auditor role
Status: accepted (improvements.md 2.5, part). Extends ADR-0011 (encryption at rest).

## Context
Every encrypted file's key was derived from the master key and the file id: a document could not be made unreadable without destroying the master key for everything. The only login protection was an nginx rate limit per IP. No role could audit without also being able to read documents.

## Decision
- **Per-file random keys.** Each newly encrypted file (direct and chunked uploads) gets a random 32-byte key, stored ONLY wrapped (AES-256-GCM under a key derived from the master key, bound to the file id) in `file_keys`. The file itself is still encrypted by `crypto_envelope` with a key derived from that file key. Files encrypted before this change, and meter readings, keep the old master-derived key: there is no row, `keystore.material()` falls back, and nothing needs migrating.
- **Erasure** (`POST /files/{id}/erase`, admin, `connection_docs` only): the wrapped key is destroyed (tombstone, `status = erased`) and the stored objects (primary and replica) are deleted. Downloads, verification and receipts answer 410. The metadata row and the audit trail stay: that it existed, who read it and who erased it must remain provable. Proof: a ciphertext copied out beforehand and restored afterwards is still unreadable. The scrubber does not treat an erased file as damaged (no alert).
- **Master-key rotation without re-encrypting any file**: `keystore.rewrap_all(repo, old, new)` re-wraps the small keys only (tested: not one stored object changes). Rotation is available as a function, not wired to a button: it needs both keys at once and a restart with the new one.
- **Login lockout with backoff**: after `LOGIN_MAX_FAILURES` (5) consecutive failures an account is refused (429 with `Retry-After`) for 30 s, doubling per further failure up to 15 min. Unknown accounts are tracked the same way, so the answer never reveals whether an account exists. A success resets it. The moment of locking is audited once and counted (`filegrid_logins_total{outcome}`).
- **Auditor role** (`auditor@ppc.ro`, password generated by the start scripts, optional): reads the file list, audit trails and `GET /audit/verify`; cannot download, verify, request receipts, upload, change policies or erase.

## Limits (stated plainly)
- A backup of the DATABASE taken before an erasure still contains the wrapped key; erasure is complete only once such backups age out. Crypto-shredding protects copies of the ciphertext (storages, replicas, storage snapshots), not copies of the key table.
- Files stored before this change cannot be crypto-shredded (their key is derived): erasing one deletes its objects only, and says so (`method: objects_deleted_only`).
- Lockout can be used to lock a real account out on purpose (a denial of service); the cap is 15 minutes, the nginx per-IP limit stays in front, and the audit trail shows it happening.
- Staged upload chunks are still encrypted under the master-derived key (they live minutes, then are deleted).
- Not done from improvements.md 2.5: per-meter credentials (needs the simulator, a teammate's code, and a provisioning flow), ClamAV scanning, signed short-lived download links, TOTP for admin.

## Proof
`scripts/demo/erase-document.sh` passed on the live stack (own wrapped key, ciphertext not readable, erase, 410, restored ciphertext still unreadable, auditor can read the trail but gets 403 on content, sixth wrong password answers 429); 24 unit tests (`test_security.py`).
